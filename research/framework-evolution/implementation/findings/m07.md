# M07 — minimal public-Eve Next application

Date: 2026-09-06. Branch: `codex/m07-minimal-next-eve`.
Baseline: `18db694b` (AI SDK 7 migration, PR #308).

## Result

Implemented a runnable, isolated [Next source example](../../../../examples/minimal-next/README.md)
using published Eve 0.52.1, AI SDK 7.0.93, Next 16.3.0, OpenAI 4.0.59,
Node 24.20.0 and Postgres World 5.0.0-beta.40. The exact isolated Bun graph is
[committed](../../../../examples/minimal-next/bun.lock); it does not modify
`apps/chat`, the root lockfile, or another worktree.

The linear application works with a real provider: create, stream, follow-up,
pending approval, typed project-local rendering, reconnect and cooperative
cancellation. Trusted owner → conversation → Eve session bindings persist in a
separate application schema. The public application API is tRPC 11.16.0, aligned
with [the resolved service decision](https://github.com/FranciscoMoretti/chat-js/issues/290#issuecomment-5552646959).
No private Eve patch, historical-branch contract, alternate package manager,
registry system, or unrelated demo dependencies were introduced.

This is a **bounded implementation for review**, not an unconditional supported
production recipe. Automatic recovery of ambiguous creation and prompt provider
abortion remain outside the proven contract. The independent upstream-audit task
received the concrete cancellation and empty approval-turn-ID observations.

## Exact limits and alternatives

### Creation is fail-closed, not distributed create-once

`lib/bindings.ts` commits a unique `(owner_subject, operation_id)` reservation
before the Eve HTTP call. A matching bound retry returns the original mapping;
there is no cross-caller in-flight promise. Unknown outcome or a crash leaves an
unresolved reservation. The ID is never returned before its owner mapping is
persisted, and an orphan cannot be read through the application gateway.

Public Eve creation accepts `operationId`, but its inspected implementation
resolves then creates. No cross-process atomicity guarantee was inferred from
that lookup. The implemented safe alternative is operator reconciliation with
no automatic re-execution. Promoting transparent crash-time creation recovery
requires a proven atomic create/lookup contract or an independently demonstrated
public composition. Clearing reservations and retrying is not an acceptable
substitute. This example does not automatically release Workflow worker locks.

### Cancellation occurs at a cooperative boundary

In one long model step, `turn_3` started at `07:28:41.140Z`, completed at
`07:29:28.590Z`, and `turn.cancelled` followed at `07:29:28.636Z`. Eve accepted
cancellation earlier, but generation continued through the active step. Its
response stream may settle before the late cancellation event; replay is the
authoritative check. A shorter repeat also verified acceptance and a new durable
cancellation event. No claim of immediate provider abort or refunded usage is
made. A worker interruption during browser streaming surfaced a network error;
the Reconnect control restored that conversation from durable execution data.

The safe implemented option is cooperative cancellation with explicit semantics.
If product acceptance requires prompt abort of active provider work, that is an
upstream/runtime acceptance gate, not a UI label or local stream-abort workaround.

### Other limits

- Raw Eve/Workflow callbacks remain on an internal loopback worker listener.
  Only Next is an application ingress. This is not a validated public callback
  deployment recipe; no deployment or upstream submission occurred.
- Approval continuation in this release emitted `turn.completed` with an empty
  turn ID at sequence 1; ordinary later sends produced `turn_2`, `turn_3`, etc.
  The UI retains Eve's projection semantics rather than inventing execution IDs.
- Recovery used graceful process restart and real Postgres storage, not a
  multi-replica or forced-worker-lock recovery claim. Database outage, provider
  retry idempotency and external side-effect recovery are not established.
- The source example is independently runnable. CLI graph materialization and
  selected external registry installation are downstream integration work.

## Fresh browser verification and cancellation follow-up fix

A subsequent user-requested browser pass found a real gap: after Stop, the next
send could consume a late boundary from the cancelled turn and settle without
rendering its own accepted response. The browser recovered it with Reconnect.
`lib/send-turn.ts` now performs supported public catch-up after the next command
following accepted cancellation; ordinary sends do not incur this extra replay.
The live cancellation proof asserts a newly appended assistant response after
cancellation, excluding older matching messages.

Fresh headed-Chrome evidence passed: exact `BROWSER_SEND_OK` response; pending
approval survives Reconnect; owner approval renders the typed confirmation;
rejection clears the request without confirming the declined note; Stop produces
a matching durable `turn.cancelled`; a later send renders
`BROWSER_AFTER_STOP_OK` without manual reconnect. A browser using another owner
received 404 for both conversation resolution and stream attachment. The HTTP
matrix again passed its 28 recorded checks. A 390px mobile viewport had no
horizontal overflow, and axe 4.12.1 reported 33 passes and zero violations.
Next's compilation and runtime diagnostics were empty. Cooperative cancellation
and ambiguous creation limitations above still apply.
