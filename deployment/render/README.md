# Render hosting candidate

This source-clone profile runs ChatJS on Render with external PostgreSQL and private files. It is a reproducible configuration candidate for #650, **not hosted certification**. Remote deletion/guest retention, actual Supabase privileges, OAuth and restart recovery remain acceptance gates. Do not use it for real user data until those gates pass.

## Topology

Select `deployment/render/render.yaml` as the Blueprint path with the repository root as the build root. Importing it creates billable web and cron services. This change does not provision them. Automatic deployments are disabled.

One Node 24.20.0 web instance runs `next start` on `0.0.0.0:10000`. The pinned `@chat-js/eve@0.61.0-chatjs.0` integration starts two Node children from `apps/chat/.output/server/index.mjs` and `apps/chat/guest/.output/server/index.mjs` on loopback ports 4274/4275. Next rewrites `/eve/chat/v1/*` and `/eve/guest/v1/*` to those processes. Their PostgreSQL world runs its durable queue in those processes. Do not add an independent `eve:start` worker or set `EVE_NEXT_PRODUCTION_ORIGIN` for this layout.

Keep the full source-clone build output and dependencies, including both `.output` trees. This is not a standalone Next image or a certified Docker layout. Do not set `VERCEL`, `VERCEL_ENV`, `VERCEL_URL` or `EVE_BASE_URL` from a previous deployment. Workflow world selection must stay PostgreSQL across build and runtime.

`/api/health` checks the application database and both workers within 4.5 seconds, returning only ready/unavailable. `EVE_INTERNAL_ORIGIN=http://127.0.0.1:10000` makes these probes and internal gateway calls local. It is separate from the public HTTPS `APP_URL` used by Better Auth. A worker exit makes the entire instance unhealthy. Render's HTTP health checks remove unhealthy instances and restart them after sustained failure. Abrupt termination still requires durable workflow recovery, tested separately below.

## Prepare the selected source and secrets

Use the existing installer/registry to select an alternative gateway and Supabase storage before building. The checked-in demo defaults still use Vercel Gateway/Blob and Vercel Sandbox. The blueprint deliberately does not overwrite installed source or silently switch providers. Installer validation and executable selection documentation are owned by #654 / PR #660.

Required provisioning inputs:

- A Render account and authorization to create the web and scheduled services, with an agreed public HTTPS origin.
- A fresh Supabase application database, private storage bucket and server credentials for the selected `files-sdk/supabase` adapter. Use the generated environment requirements rather than exposing a service role key through `NEXT_PUBLIC_*`.
- `DATABASE_URL` and, when needed, `DATABASE_MIGRATION_URL` for the application. `WORKFLOW_POSTGRES_URL` must be a direct or session connection. Supabase transaction pooling on port 6543 is rejected by existing validation. Direct connectivity can require IPv6 support or Supabase's IPv4 option; session pooling on port 5432 is a candidate, not proof of LISTEN/queue compatibility.
- Independent `AUTH_SECRET`, `EVE_GATEWAY_SECRET` and `CRON_SECRET` (generated by the blueprint). Keep these stable across restarts. Add the selected gateway, search and file credentials to the web service before the first build. Secrets are needed by build-time validation as well as runtime.
- GitHub or Google OAuth credentials with callback `https://YOUR_ORIGIN/api/auth/callback/github` or `/google`. Keep Better Auth, not Supabase Auth.

Leave `TRUSTED_CLIENT_IP_HEADER` unset until the edge contract is verified. Existing guest admission deliberately refuses a missing or multi-valued trusted IP. Render documents `X-Forwarded-For`, but that alone does not prove a single unspoofable value for this application. Test a forged incoming header against the real edge or put an operator-controlled proxy in front that overwrites one single-IP header and prevents bypass. Do not select an arbitrary leftmost forwarded address. Signed-in acceptance can proceed while guest admission remains blocked.

Omit analytics, Speed Insights and Langfuse through their existing feature selections if desired. No replacement implementation is needed. The non-Vercel sandbox adapter belongs to #649 and must be installed before claiming a Vercel-free tool profile.

## Initialize and build

Run these commands from the repository root using Node 24.20.0 and Bun 1.3.1, with the selected environment exported. Use a fresh isolated database for first acceptance.

```sh
bun install --frozen-lockfile
bun run --cwd apps/chat setup
bun run --cwd apps/chat eve:check
bun run --cwd apps/chat build
cd apps/chat
node node_modules/next/dist/bin/next start --hostname 0.0.0.0 --port 10000
```

`setup` explicitly runs application migrations and workflow setup. It requires DDL permissions for application tables, `workflow`, `workflow_drizzle`, `graphile_worker`, functions, triggers and queue objects. On the audited commit, remote setup checks core tables but does not install the lifecycle fences. Merely passing `eve:check` does not certify remote cleanup. The deployment build checks persisted world identity and does not automatically migrate a non-Vercel database. Before each rollout, run the explicit setup/migration step under operator control. Do not redirect an existing managed Workflow database to PostgreSQL or change its world identity.

If the Supabase role or connection cannot meet Workflow requirements, use a separate dedicated PostgreSQL database for `WORKFLOW_POSTGRES_URL` and repeat setup and acceptance there. Keep application data on Supabase. No separate provider implementation is needed, but remote lifecycle acceptance is still required. Never bypass compatibility checks or simulate a remote database as loopback to enable deletion.

## Scheduled cleanup and provider dependency

The cron service calls the existing `/api/cron/cleanup` at 02:00 UTC with the shared bearer secret. `scripts/hosted-cleanup.ts` rejects redirects, non-HTTPS origins, HTTP errors and bodies without `success: true`. It repeats successful guest batches until a batch deletes zero families, with one 120-second deadline and a 100-request limit; reaching either bound requires retry. It prints no response payload or credentials and exits nonzero when cleanup is partial, unsupported or failed. Inspect protected application logs and rerun after fixing the cause. A timeout is uncertain, so rely on the route's idempotent claim/retry behavior rather than declaring deletion complete.

The current remote lifecycle gate will make this cron fail truthfully. #652 / merged PR #656 owns the native provider compatibility/fence contract; #651 / merged PR #658 wires callers to it. The initial base `881acebba08f3479a7129eeae768bdf3a183992d` includes #656 and earlier reporting fixes but not #658. Even the reviewed #658 contract intentionally limits support to loopback. This work does not duplicate or loosen that guard.

Before remote cleanup can be accepted, its owner must supply remote setup plus evidence for compatibility, durable retirement, late writes, inventory, queue purge and payload erasure. The sandbox adapter must expose ownership-scoped resource inventory and idempotent termination/deletion, retain uncertain resources for retry, and not report absence or successful erasure merely because its service is unreachable. Native payloads must remain until external resources are accounted for. The current provider's `sandboxLifecycle: false` is not a sandbox erasure guarantee.

Before calling this profile hosted, record the exact commit, installed provider IDs, dependency versions, commands and redacted evidence for:

1. Fresh setup against the actual Supabase role and connection, including queue LISTEN/NOTIFY and lifecycle compatibility. Repeat with a dedicated Workflow database if required.
2. Build/start with both workers, health 200, deliberate worker failure producing health 503, whole-instance replacement, and a running conversation resuming after restart without duplicate messages or usage.
3. Streaming through the real Render edge (`curl -N` or the browser), cancellation, reload/resume, edit/regenerate, share/copy and ownership isolation. Observe progressive chunks before completion, not merely a final response.
4. OAuth round trip and origin rejection, spoofed/multiple client-IP inputs and valid guest admission only after the proxy contract is established.
5. A private Supabase upload that an unauthenticated raw URL cannot read, authorized download, copy, original deletion with the copy intact, then final deletion. Run these with two users to check isolation.
6. Expired guest and orphan-file cleanup, failure/retry, unknown sandbox resources, interrupted deletion, late-write rejection and final native/resource erasure. Confirm cron failure on unsupported/skipped/pending work and success only after completion.
