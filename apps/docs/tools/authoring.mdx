Author tools as real TypeScript files that you can import, type-check, and test. Canonical implementations live in `packages/registry/src/tools/<id>/`. The app consumes installed copies through local imports.

## Native execution

Every installed or custom tool uses EVE's `defineTool()`. EVE owns input validation, execution, approvals, and model-output policies. Use the shared receipt helper when your tool reports costs:

```ts
import { defineTool } from "eve/tools";
import { z } from "zod";

import { toolResultToModelOutput } from "@/lib/eve/tool-model-output";
import { executeWithToolUsage } from "@/lib/eve/tool-usage";

export const textStats = defineTool({
  description: "Count words in text",
  inputSchema: z.object({ text: z.string() }),
  execute: ({ text }, context) =>
    executeWithToolUsage(context, (usage) => {
      usage.addCostUsd(0);
      return { words: text.trim() ? text.trim().split(/\s+/).length : 0 };
    }),
  toModelOutput: toolResultToModelOutput,
});
```

`executeWithToolUsage` accepts JSON-compatible outputs. A result explicitly has `status: "success"` and a typed `output`, or `status: "error"`, a sanitized error, and `output: null`. The common `toolResultToModelOutput` projection keeps usage and progress out of model context. Renderers receive the visible output after receipt validation.

Call `usage.addCostUsd()` for known provider costs in US dollars. Report `0` for explicitly free work. An omitted report leaves the cost unknown. Call `usage.markUnknown()` when any part of the total cannot be determined, even if you already reported a known subtotal. Unexpected exceptions propagate unchanged to EVE, including authorization signals. Cancellation also propagates. Pass EVE's `context.abortSignal` to provider calls so they can cooperate with cancellation.

Use `return usage.fail()` only for an expected domain failure that should produce a sanitized error receipt with reported costs—for example, storage failing after a paid generation. This is a returned application result, so EVE records a completed action. Throwing instead produces EVE's native failed action and does not produce a final cost receipt. Do not wrap an entire tool or native authorization calls in `.catch(usage.fail)`.

`executeWithToolProgress` uses the same receipts and accumulator for streaming executions. Its callback can publish intermediate output and JSON progress. The native research workflow yields durable phase/topic snapshots with the same receipt shape. Research schemas are kept outside the generic receipt contract.

EVE may interrupt execution before a final receipt settles. These helpers do not guarantee accounting for every external request or prevent duplicate provider work. Use provider idempotency and reconciliation where required. Workflow tools require their own integration with durable workflow steps.

## Renderer

Export a renderer built with `defineToolRenderer`. It validates persisted input and output against your schemas before calling your component. Renderer props are inferred from those schemas, without importing the server tool:

```tsx
"use client";

import { z } from "zod";
import { defineToolRenderer } from "@/chatjs/core/tools/define-renderer";

export const TextStatsRenderer = defineToolRenderer({
  inputSchema: z.object({ text: z.string() }),
  outputSchema: z.object({ words: z.number() }),
  render: ({ tool }) =>
    tool.state === "output-available" ? (
      <p>{tool.output.words} words</p>
    ) : (
      <p>Counting words…</p>
    ),
});
```

Keep shared schemas in `schemas.ts`. For a separate view component, use `ToolRendererProps<typeof inputSchema, typeof outputSchema>` from the same helper module. The validated renderer handles malformed results, approvals, denied requests, and errors.

## Shared definitions

You can share schemas, description and display metadata through a pure module:

```ts title="definition.ts"
import { z } from "zod";
import type { ToolDefinition } from "@/chatjs/core/tools/tool-definition";

export const toolDefinition = {
  name: "textStats",
  description: "Count words in text",
  inputSchema: z.object({ text: z.string() }),
  outputSchema: z.object({ words: z.number() }),
  display: { name: "Word count", shortName: "Word count" },
  selectable: true,
} as const satisfies ToolDefinition;
```

Use `toolDefinition.description` and `.inputSchema` in `defineTool`, and `.inputSchema` and `.outputSchema` in `defineToolRenderer`. Keep EVE execution and receipt policy in `tool.ts`. This definition is metadata, not another tool execution API.

Add `"definitionExport": "toolDefinition"` beside the registration's `toolExport` in its descriptor and include `definition.ts` in its file list. The CLI emits a typed static import. The definition name must match the registration name, including a provider slot when selected. Imports are not executed by the installer. App composition rejects duplicate definition names.

`selectable: true` exposes the name to the composer selection contract. Display metadata supplies labels with a default icon. Descriptor `composer` metadata can supply a specific icon and takes precedence. Existing tools without a shared definition continue using descriptor metadata. Historical messages preserve removed tool names so that their selection can be shown as unavailable instead of becoming automatic.

## Files and viewers

Use EVE's native sandbox tools for document creation and editing. Install `attach-workspace-file` to deliver immutable snapshots through ChatJS storage. A tool can offer a rich result renderer without requiring a viewer plugin. File cards dispatch to optional viewers by media type, with download as the fallback. See [Documents & Files](/tools/canvas).

## Item metadata

Declare the tool’s source files, targets and package dependencies in its registry item. The built-in image and video items in `packages/registry/registry-items.ts` illustrate the layout. This JSON shows the ChatJS metadata for the word-count tool.

```json
{
  "contractVersion": 1,
  "kind": "tool",
  "id": "text-stats",
  "tools": [
    { "toolExport": "textStats", "rendererExport": "TextStatsRenderer" }
  ],
  "envRequirements": []
}
```

Use `contractVersion: 1` for a UI-independent descriptor. Version 2 additionally declares `uiBase: "base"` or `"radix"` for UI compatibility. Neither selects an execution implementation. The same metadata is emitted as `meta.chatjs` in the registry item and as an installed `chatjs/tools/text-stats/chatjs.json` descriptor.

A registry item can register several native tools through its `tools` array. Each export comes from the item’s `tool.ts`, and optional renderers come from `renderer.tsx`. Registration names must be unique across all installed items. Provider slots register exactly one tool.

Items target files under `~/chatjs/tools/<id>/`. Declare npm packages in `dependencies` or `devDependencies`, and shared registry items in `registryDependencies`. EVE and the ChatJS receipt/renderer helpers are supplied by the host app.

Keep credential reads and format validation in a server-only module owned by your tool, such as `my-tool-env.ts`. Read credentials when the tool runs. Do not add tool credentials to the core `lib/env-schema.ts` or import them into configuration schemas used by client code. Two tools can read the same environment variable independently.

For the shared installation checklist and `check-env` command, declare credential alternatives in the typed metadata:

```ts
const envRequirements = [{ options: [["MY_TOOL_API_KEY"]] }];
```

Every outer requirement must be satisfied. Within a requirement, `options` lists alternatives, and each alternative lists variables needed together. The app validates these requirements without evaluating remote source.

## Configuration

A tool can declare `"config": { "key": "myTool" }` in its descriptor and install `configuration-schema.ts` alongside `tool.ts`. Export a Zod schema named `configSchema`. Its input becomes `ai.tools.myTool` in the app's single `chat.config.ts`, and its output becomes the parsed runtime configuration. Supply defaults for omitted fields and for the omitted object:

```ts title="configuration-schema.ts"
import { z } from "zod";
import { languageModelSchema, modelRoles } from "@/lib/config-models";

const configSchema = z
  .strictObject({
    model: languageModelSchema.default(modelRoles.balanced),
  })
  .prefault({});

export { configSchema };
```

Use `modelRoles.smart`, `.balanced` or `.fast` for language models. Image and video roles are optional and require the corresponding gateway capability. These modules must be pure and safe to import in the browser: do not import runtime `config`, credentials, server SDKs or the tool implementation. The CLI generates typed imports without executing the module during installation. It rejects duplicate keys and the reserved core key `followupSuggestions`.

## Provider selections

An optional `slot` selects a product feature independently of the execution contract. Supported values are `generateImage` and `generateVideo`. The CLI registers that item under the selected feature name and applies its existing feature toggle. Only one item can occupy each selection.

A slot does not impose an input schema, output schema, or renderer. A renderer is optional.

Deep research uses EVE agent copies to access the parent's installed tools and connections. EVE owns discovery, validation, approvals, authentication, and cancellation. Native copies inherit the parent's model setup and optional application billing hooks; research adds no orchestration charge.

## Installable workflows

`chat-js add deep-research` installs native workflow files under `agent/tools` and `agent/lib/research`, plus optional ChatJS progress presentation. It does not install a search adapter, storage provider, or document editor. Use native EVE connections and model settings; workflow-specific bounds live in `agent/lib/research/configuration.ts`. Research returns a sandbox path, and the calling agent handles file delivery separately.

Workflow registrations declare `workflow: true` alongside their `toolExport` and optional `rendererExport`. The bundle installs an ordinary EVE default export at `agent/tools/<toolExport>.ts`; its `tool.ts` re-exports that definition by name for type inference. The CLI keeps workflows out of the dynamic tool set and generates type-only registrations for their UI. EVE discovers and executes the static entry point itself.

A bundle can declare `availabilityExport`, naming a predicate in `availability.ts`. The generated availability registry filters model exposure. Keep an execution guard in the workflow's preparation step as well. An unavailable tool must not rely on model filtering alone for authorization.

To remove research, delete `chatjs/tools/deep-research`, `agent/tools/deepResearch.ts`, and `agent/lib/research`, then run `chat-js sync`.

Renderers can declare an `updateSchema` and `renderProgress` component. ChatJS validates receipt updates before rendering them and retains valid progress when the receipt reports an error.

## Native services and custom tools

Tools receive EVE's native context. Import only the ChatJS services your implementation needs: authorized file upload, model access and pricing, or image context. The media and file-publication sources show these integrations. Services are not supplied through a second optional execution-context object.

Keep provider credentials and SDK dependencies in the installed integration. Tools accessing private user data must authorize that access using the native session identity. Both official and third-party tools use the same registration and accounting contract.

For local custom tools, add native definitions to `integrations/tools/execution.ts` with `defineToolSet` from `@/lib/eve/tool-types`. This checks each definition without widening its concrete input/output types. Add renderers in `integrations/tools/ui.ts`, and shared metadata in the client-safe `integrations/tools/definitions.ts`. Retain the installed spreads and native workflow-name guard. App-owned composition may explicitly replace installed tools; installed descriptors cannot duplicate each other.

## Build and verify

```bash
bun run --cwd packages/registry test:types
bun run --cwd packages/registry test:unit
bun run --cwd packages/registry build
```

The build script emits `registry.json`, then pinned shadcn reads the sources and generates `dist/r/*.json`. Publish those generated files from your registry endpoint.

Install the item into an independent ChatJS app and type-check it. Exercise it through an EVE worker to verify durable execution, rendering, cancellation, and usage where relevant:

```bash
npx chat-js@alpha add https://example.com/r/text-stats.json
```
