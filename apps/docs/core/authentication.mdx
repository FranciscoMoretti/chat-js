ChatJS uses Better Auth for account sessions. EVE requests pass through the authenticated ChatJS gateway, which enforces access to the selected conversation. Plugin installation can add guest access or public sharing without granting access to private account data.

## Session Lifecycle

1. User clicks **Continue with [Provider]** and is redirected to the provider's authorization URL.
2. After approval, the provider redirects back to `/api/auth/callback/[provider]`.
3. Better Auth exchanges the code for tokens, upserts the user in the database, and creates a session.
4. A signed HttpOnly session cookie is set on the browser.

Sessions are stored in Postgres. A short-lived cookie cache reduces database hits. Most session validations are resolved from the cookie itself rather than a database query.

---

## Guest Chat

Install [Guest Chat](../plugins/guest-chat) to let visitors start disposable text conversations without an account. Without it, signed-out visitors at `/` are redirected to `/login`.

The plugin owns its signed credentials, session policy, IP rate limits, and cleanup inventory. Its fixed model has no tools or files. Guests have no monetary balance and cannot access account APIs or history. Signing in does not migrate the temporary transcript.

Core account authentication remains in Better Auth. The shared EVE agent requires a verified account authenticator for account hooks and capabilities. A guest or unknown session cannot gain those capabilities through reconnect credentials.

---

## Access boundaries

Account routes require a registered principal. Public authentication routes and installed public-sharing or guest flows apply their own access policies. Signing in does not grant access to another user's private conversations.

Account chat handlers require a registered principal. Guest Chat installs a separate bootstrap adapter and native authenticator that enforce its session policy.
