title: Environment Variables
description: "Look up the environment variables for application data, authentication, EVE workflows, and the gateway, storage, and plugins installed in your app."
---

Use the generated `.env.example` for your installation. Core settings live in `lib/env-schema.ts`. Installed providers, tools, and plugins declare additional requirements. Run `npm run check-env` from your app to validate the combination.

<Callout type="note">
  Missing required variables will cause the build to fail immediately. Variables
  that are required only when a feature or gateway is enabled are validated
  based on your `chat.config.ts` settings and installed feature descriptors.
</Callout>

## Required

These variables must be set for the EVE-backed application.

| Variable | Description | How to get it |
| --- | --- | --- |
| `DATABASE_URL` | PostgreSQL connection string | Use the connection string from your [PostgreSQL provider](/reference/database#connection-settings). |
| `AUTH_SECRET` | Secret used to sign and encrypt session tokens (Better Auth) | Run `openssl rand -base64 32` or use [generate-secret.vercel.app/32](https://generate-secret.vercel.app/32) |
| `EVE_GATEWAY_SECRET` | Private credential for the ChatJS gateway to call EVE | Run `openssl rand -base64 32` a second time to generate a different value from `AUTH_SECRET` |

Configure at least one OAuth provider and the connection required by your installed gateway. The integrated worker has defaults for its internal origin and local workflow database. See [EVE runtime settings](#eve-runtime-and-trusted-proxy-headers).

## Authentication

Enable providers in `chat.config.ts` under `authentication`. At least one must be enabled. The build validator checks that every enabled provider has its corresponding env vars set.

See [authentication setup](/customization/authentication) for a complete configuration example and the callback URLs.

### GitHub OAuth

| Variable             | Description                    |
| -------------------- | ------------------------------ |
| `AUTH_GITHUB_ID`     | GitHub OAuth app client ID     |
| `AUTH_GITHUB_SECRET` | GitHub OAuth app client secret |

**Setup:** Go to [GitHub Developer Settings](https://github.com/settings/developers) → **New OAuth App**. Set the callback URL to `https://yourdomain.com/api/auth/callback/github`.

### Google OAuth

| Variable             | Description                    |
| -------------------- | ------------------------------ |
| `AUTH_GOOGLE_ID`     | Google OAuth 2.0 client ID     |
| `AUTH_GOOGLE_SECRET` | Google OAuth 2.0 client secret |

**Setup:** Go to [Google Cloud Console](https://console.cloud.google.com/apis/credentials) → **Create credentials** → **OAuth 2.0 Client ID** (Web application). Add `https://yourdomain.com/api/auth/callback/google` as an authorized redirect URI.

### Vercel OAuth

| Variable                   | Description              |
| -------------------------- | ------------------------ |
| `VERCEL_APP_CLIENT_ID`     | Vercel App client ID     |
| `VERCEL_APP_CLIENT_SECRET` | Vercel App client secret |

Create a Vercel App and register its sign-in redirect URL. [Vercel OAuth setup](/customization/authentication#vercel)

## AI Gateways

Choose a gateway during creation or use the CLI to replace the installed gateway. Configure the environment for that adapter. [Gateway selection](/gateways/overview)

### Vercel AI Gateway (default)

The default gateway discovers models from the Vercel AI Gateway catalog.

| Variable | Required | Description |
| --- | --- | --- |
| `AI_GATEWAY_API_KEY` | Self-hosted / local dev | API key for Vercel AI Gateway |
| `VERCEL_OIDC_TOKEN` | Auto-set on Vercel | OIDC token injected automatically on Vercel deployments |

<Callout type="tip">
  On Vercel deployments, `VERCEL_OIDC_TOKEN` is injected automatically. You only
  need `AI_GATEWAY_API_KEY` for local development or non-Vercel hosting.
</Callout>

**Setup:** Go to [Vercel AI Gateway](https://vercel.com/ai-gateway) and create an API key.

### OpenRouter

Provides access to hundreds of models with per-token pricing.

| Variable             | Required | Description                              |
| -------------------- | -------- | ---------------------------------------- |
| `OPENROUTER_API_KEY` | Yes      | Your OpenRouter API key (`sk-or-v1-...`) |

**Setup:** Create an account at [OpenRouter](https://openrouter.ai), then go to [API Keys](https://openrouter.ai/keys).

### OpenAI

Direct connection to the OpenAI API. Use when you only need OpenAI models.

| Variable         | Required | Description                    |
| ---------------- | -------- | ------------------------------ |
| `OPENAI_API_KEY` | Yes      | Your OpenAI API key (`sk-...`) |

**Setup:** Follow the [OpenAI quickstart](https://developers.openai.com/api/docs/quickstart) to create an API key.

### OpenAI Compatible

The adapter lists models at `/models` and sends chat requests to `/chat/completions` under the same base URL. Configure a bearer token if your server requires one. [Compatible endpoints](/gateways/openai-compatible)

| Variable | Required | Description |
| --- | --- | --- |
| `OPENAI_COMPATIBLE_BASE_URL` | Yes | Base URL of the compatible API (e.g., `http://localhost:11434/v1`) |
| `OPENAI_COMPATIBLE_API_KEY` | If required by the endpoint | API key for the compatible provider |

**Setup:** Start your compatible server (for example, run `ollama serve` for Ollama), set `OPENAI_COMPATIBLE_BASE_URL` to its `/v1` endpoint and set `OPENAI_COMPATIBLE_API_KEY` if the endpoint requires authentication.

### LiteLLM

Routes requests through a LiteLLM proxy for centralized model access, key management, routing, and spend tracking.

| Variable | Required | Description |
| --- | --- | --- |
| `LITELLM_BASE_URL` | Yes | API base URL used for inference (e.g., `http://localhost:4000/v1`) |
| `LITELLM_API_KEY` | Optional | Master key or virtual key if your LiteLLM proxy requires authentication |

Set the base URL to the prefix your proxy uses for chat completions. Supply `LITELLM_API_KEY` when the proxy requires authentication. [LiteLLM setup](/gateways/litellm#setup)

## Features

Installed tools and plugins declare their environment requirements. For example, attachment uploads need durable file storage and a sandbox that supports persistent files. Configure the credentials for both providers. [Attachment uploads](/plugins/attachments)

### Web search connections

[Web search connections](/tools/web-search) declare their own credentials. Firecrawl uses `FIRECRAWL_API_KEY`, and Tavily’s registry connection uses Vercel Connect.

### MCP Connectors

Install [Model Context Protocol](https://modelcontextprotocol.io) connectors to expose custom tools and data sources to the AI:

```bash
chat-js create my-chat --mcp
# Or, inside an existing app:
chat-js add mcp
```

Installed registrations determine availability. You must configure `MCP_ENCRYPTION_KEY` whenever MCP is installed, including before any connectors are added.

| Variable | Required | Description |
| --- | --- | --- |
| `MCP_ENCRYPTION_KEY` | Yes | 44-character base64 key used to encrypt stored MCP server credentials (URLs, OAuth tokens) |

**Generate a key:**

```bash
openssl rand -base64 32
```

<Callout type="note">
  The key must be exactly 44 characters (32 bytes encoded as base64). Changing
  this key after deployment will invalidate all stored MCP connector
  credentials.
</Callout>

### Postgres Hosting

`DATABASE_URL` is the runtime connection. Set `DATABASE_MIGRATION_URL` when your host provides a separate direct endpoint for schema operations. It falls back to `DATABASE_URL` when omitted. Set `DATABASE_PREPARE=false` for a transaction pooler without prepared-statement support, and optionally set `DATABASE_MAX_CONNECTIONS` to a positive per-process limit. See [Database](/reference/database) for deployment behavior.

### File Storage

Attachments, image generation, and video generation require a durable storage adapter compatible with Files SDK. Storage requirements are generated from the selected provider and validated by `scripts/check-env.ts`.

Provider credentials belong in environment variables or the provider SDK's credential chain. Non-secret adapter options belong in `chatjs/providers/storage-options.ts`. See [File storage](/storage) and the [Files SDK provider reference](https://files-sdk.dev/docs/providers) for the requirements of your selected provider.

<Callout type="tip">
  When using Vercel Blob, connect a store in your project dashboard under
  **Storage**. Use the connected store’s `BLOB_READ_WRITE_TOKEN`, or configure
  `BLOB_STORE_ID` with `VERCEL_OIDC_TOKEN` for OIDC authentication.
</Callout>

### Code Execution Sandbox

Select a native EVE environment in `agent/sandbox.ts`. Docker and Vercel Sandbox run Python and Node; just-bash provides a simulated shell. There is no ChatJS execution feature flag. See [Sandboxes](/deployment/sandboxes) for selection and native image configuration.

The following credentials apply when choosing Vercel Sandbox:

| Variable | Required | Description |
| --- | --- | --- |
| `VERCEL_OIDC_TOKEN` | Auto-set on Vercel | Used automatically for OIDC auth on Vercel deployments |
| `VERCEL_TEAM_ID` | Self-hosted only | Your Vercel team ID (`team_...`) |
| `VERCEL_PROJECT_ID` | Self-hosted only | Your Vercel project ID (`prj_...`) |
| `VERCEL_TOKEN` | Self-hosted only | Vercel API token with sandbox permissions |

<Callout type="note">
  On Vercel deployments, sandbox authentication happens automatically via OIDC,
  so no additional variables are needed. Set `VERCEL_TEAM_ID`,
  `VERCEL_PROJECT_ID`, and `VERCEL_TOKEN` only when running ChatJS outside of
  Vercel.
</Callout>

## EVE runtime and trusted proxy headers

| Variable | Description |
| --- | --- |
| `EVE_GATEWAY_SECRET` | **Required.** Private credential used between ChatJS and EVE. Generate independently from `AUTH_SECRET` with `openssl rand -base64 32`. Rotating `AUTH_SECRET` does not rotate this credential. |
| `WORKFLOW_POSTGRES_URL` | **Local/self-hosted only.** Optional direct/session Postgres connection for registered-chat workflows. Defaults to `DATABASE_URL`. Never uses `DATABASE_MIGRATION_URL`. Unused on Vercel deployments. |
| `EVE_INTERNAL_ORIGIN` | Optional application gateway origin serving `/eve/chat/v1/*`. Defaults to `https://${VERCEL_URL}`, then the origin of `APP_URL` or `PLAYWRIGHT_TEST_BASE_URL`, then `http://localhost:${PORT}` (port 3000 by default). |
| `VERCEL_AUTOMATION_BYPASS_SECRET` | Server-only deployment-protection bypass credential for calls to this Vercel project. Required when protection blocks internal EVE requests. |
| `TRUSTED_CLIENT_IP_HEADER` | Optional self-hosted reverse-proxy header that contains one verified client IP. The proxy must overwrite any caller-provided value. Vercel uses its native trusted header. |

`DATABASE_URL` stores application identity and metadata everywhere. Vercel Preview and Production use managed Workflow for EVE execution and transcripts. Local/self-hosted registered chats use `WORKFLOW_POSTGRES_URL` and require both schemas to be initialized. Disposable guest chats keep their isolated local backend during development. See the [database setup guide](/reference/database#eve-workflow-database).

Leave `EVE_INTERNAL_ORIGIN` unset for the integrated gateway. On Vercel it follows the exact deployment URL, even when OAuth uses a stable branch alias or `APP_URL`. Derived app/test URLs discard paths, queries, and fragments, but reject credentials and non-HTTP(S) schemes. Use HTTPS for remote gateways, including private-network workers. HTTP is allowed only for loopback hosts (`localhost`, `127.0.0.0/8`, and `[::1]`). If you previously used an internal HTTP worker, configure a TLS endpoint or a loopback gateway. An override must serve the named `/eve/chat/v1/*` mount and contain no path, query, or credentials. A raw EVE worker exposing only `/eve/v1/*` is not a supported endpoint. On protected Vercel deployments, the server forwards `VERCEL_AUTOMATION_BYPASS_SECRET` only when this origin exactly matches `https://${VERCEL_URL}` or `https://${VERCEL_BRANCH_URL}`. It does not forward the credential to other origins, including arbitrary custom domains. The EVE bearer credential and owner identity are still required.

## Optional / Advanced

### Cron Job Secret

The scheduler calls `/api/cron/cleanup` with this secret. The job removes orphaned managed files and runs cleanup tasks contributed by installed plugins, including [guest session cleanup](/plugins/guest-chat).

| Variable      | Description                                                 |
| ------------- | ----------------------------------------------------------- |
| `CRON_SECRET` | Bearer token that the cron runner must send to authenticate |

**Generate a secret:**

```bash
openssl rand -base64 32
```

On Vercel, the platform automatically sends `CRON_SECRET` as an `Authorization: Bearer <secret>` header when triggering cron jobs.

### App URL

| Variable | Required | Description |
| --- | --- | --- |
| `APP_URL` | Production outside Vercel | Full public URL of the app including protocol (e.g., `https://myapp.com`) |
| `VERCEL_URL` | Auto-set by Vercel | Deployment hostname, without protocol |
| `VERCEL_BRANCH_URL` | Auto-set by Vercel | Stable branch hostname used in preview environments |
| `VERCEL_ENV` | Auto-set by Vercel | `development`, `preview`, or `production` |

The shared `getBaseUrl()` helper resolves the application origin in this order:

1. Explicit `APP_URL`.
2. `https://${VERCEL_BRANCH_URL}` when `VERCEL_ENV=preview`.
3. `https://${VERCEL_URL}`.
4. `http://localhost:3000`.

Better Auth uses `APP_URL` when set. On production Vercel deployments, its fallback is `appUrl` in `chat.config.ts`. Elsewhere, including previews, it uses `getBaseUrl()`. Register OAuth callbacks against the resulting auth origin. Do not carry a local or production `APP_URL` into a preview unless you intend to override its branch URL. This origin selection does not change `EVE_INTERNAL_ORIGIN`.

### Agent observability

Select observability integrations from EVE's instrumentation catalog in the builder's Agent tab. Configure the credentials required by the installed native integration.
