---
title: Create a plugin
description: Package source and register server, browser, and native contributions
---

Publish a standard shadcn registry item with `meta.chatjs.kind: "plugin"`. Plugin IDs use lowercase letters, digits, and hyphens, beginning with a letter. External plugins use the same metadata and sync path as the built-ins.

## Prerequisites

Use a working ChatJS app and a shadcn registry. Read [Using plugins](./using-plugins) before packaging a new capability.

## 1. Organize the source

In this repository, keep a plugin's installation manifest in `packages/registry/src/plugins/<id>/manifest.ts`, its implementation in `src/`, and its framework entrypoints in `adapters/`. Map implementation files into `~/chatjs/plugins/<id>/`. Map thin Next and EVE entrypoints into their required `app/` and `agent/` locations. List every distributed file explicitly. Tests and authoring metadata stay in the repository.

Sync generates imports for the conventional entry files listed in each plugin’s descriptor.

## 2. Define the integrations

Export a namespaced tRPC `router` from `router.ts`. For example, the MCP router groups its procedures under `mcp`. Your app merges installed routers with its own in `trpc/routers/_app.ts`.

For startup instrumentation, add `instrumentation.ts` to the descriptor's `files` list and default-export an `InstrumentationRegistration` function. The app loads that entry when it runs startup hooks.

Export `chatUi` from `chat-ui.ts` and bind its components to typed slots. Use `layout-ui.ts` with a `layoutUi` export for global layout components.

```tsx
"use client";

import { ComposerExtensions, SettingsLinks } from "@/components/chat-slots";
import { definePlugin, slot } from "@/chatjs/core/ui/slots";
import { ConnectorsControl } from "./composer";
import { ConnectorsSettingsLink } from "./settings";

export const chatUi = definePlugin({
  id: "mcp",
  slots: [
    slot(ComposerExtensions, ConnectorsControl),
    slot(SettingsLinks, ConnectorsSettingsLink),
  ],
});
```

Keep credentials and database imports in server modules. Edit the bound components directly, or wrap them with ordinary React components.

Core keeps explicit optional fields such as `projectId`. Plugins validate them against their own storage and lifecycle behavior. A separate runtime-safe `chat.ts` entrypoint participates in transactional creation, history, navigation, and deletion. See [Plugin integration points](../reference/plugin-api) for signatures and lifecycle guarantees.

## 3. Declare the installation

For example, this excerpt from the MCP descriptor shows how the file list registers the server entry point:

```json
{
  "contractVersion": 3,
  "uiBase": "base",
  "id": "mcp",
  "kind": "plugin",
  "files": ["chatjs/plugins/mcp/router.ts", "chatjs/plugins/mcp/chat-ui.ts"]
}
```

For built-in plugins, `definePluginItem` derives the installed `plugin.json` file list from the registry targets. MCP declares its database schemas and credential requirements and ships a default-exported format check in `validate-env.ts`. tRPC rejects overlapping namespaces when the app composes its routers. Each UI scope checks that plugin IDs are unique. Only one installed plugin can own uploads or model visibility.

Use `registryDependencies` to install another item and `requiresPlugins` to require its plugin ID in the installed selection. Declare `requiresStorage: true` for plugins requiring durable file storage.

Database schema paths must belong to `chatjs/plugins/<id>/`. Sync composes them for Drizzle through `chatjs/generated/installed-database.ts`. Adding or syncing a plugin preserves migration history and does not apply SQL. Environment readers belong to the plugin and remain separate from client-visible configuration.

## 4. Install and verify

Run `chat-js sync` after a direct shadcn installation. Sync validates descriptors, checks owned files, and generates TypeScript imports. At startup, Next.js runs the default function from each installed plugin’s `instrumentation.ts`.

`chat-js add` and `sync` update generated installed-plugin lists. They preserve plugin component edits and application JSX. Move slots or add local components in the layout to change placement. Within a slot, contributions follow the installed list and declaration order.

Verify both an app without the plugin and an app with it installed. Exercise the plugin's routes and UI, and check that client entrypoints cannot reach server-only code. In this repository, edit canonical source, run `bun demo:sync`, and commit the generated reference copies and mirror manifest with it.
