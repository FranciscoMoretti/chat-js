Start with a working implementation of a supported category contract:

- [Custom gateways](/gateways/custom) defines gateway exports, capabilities, credentials, and model defaults.
- [Authoring plugins](/plugins/create-plugin) defines server/client contributions, schema ownership, and framework adapters.
- [Authoring tools](/tools/authoring) defines server and renderer exports, registration descriptors, and environment requirements.

## Keep source in code

In this repository, gateway source lives under `packages/registry/src/gateways/<id>/` and tool source under `packages/registry/src/tools/<id>/`. Optional implementation source lives under `packages/registry/src/plugins/<id>/`. Declare files, dependencies, installation targets, and metadata in the item definition. Built-in gateways use `packages/registry/src/gateways/catalog.ts`, plugins have per-plugin manifests, and the media tools are defined in `packages/registry/registry-items.ts`. The top-level `packages/registry/registry.ts` assembles and validates the registry.

Use standard shadcn `dependencies` for npm packages and `registryDependencies` for shared registry items. ChatJS metadata describes the category contract. The public item name does not have to contain the category name.

## Generate and publish JSON

Run `bun run --cwd packages/registry build`. The build serializes the typed registry definition and descriptors, then runs shadcn to embed source files in `packages/registry/dist/r/*.json`. Treat these files as generated artifacts.

Publish the generated item files at your registry endpoint. Configure an alias using a URL template ending in `{name}.json`, as described in [Namespaces](/registry/namespaces). Consumers install those files through shadcn or the ChatJS CLI, and own the resulting source in their app.

Before publishing, follow [Building and Testing](/registry/testing) to check both the source and its installation into an independent app.

## Native EVE distribution

For tools that run independently of ChatJS, declare `meta.chatjs.native` with `layout`, `files` and `dependencies`. The build creates a second distribution under `dist/r/eve/` using the same source files, without UI contributions or application registry dependencies.

- `layout: "tool"` selects filenames relative to `chatjs/tools/<id>/`, including `tool.ts`. The native distribution installs them under `agent/lib/chatjs/<id>/` and adds default-export entry points under `agent/tools/`.
- `layout: "agent"` selects paths relative to `agent/` and preserves their installation targets. Use it for native workflow bundles such as Deep Research.

Declare every runtime npm dependency, including EVE. The publication audit rejects ChatJS alias imports and undeclared packages. Renderer files stay in the normal ChatJS distribution. Verify the native item with the actual EVE installer, discovery and compiler before publishing it.

Builder placement uses `agentCategory` independently of packaging. `requiresChatJS` describes application service dependencies, while Source identifies the publisher. A tool that needs application storage or document tables can still belong in Agent → Tools.

## Mirror the reference application

Use [Registry Mirror](/registry/mirror) to preview canonical source changes in `apps/chat` while root `bun dev` runs. The guide covers source locations, generated-file ownership and regeneration commands. Keep core application source in `apps/chat`.

Fresh core scaffolds exclude optional implementation source and start with empty plugin registrations. [Create](/cli/create) and [add](/cli/add) assemble the selected implementations. Application settings, permissions and runtime tool selections remain editable.
