---
title: Customize plugin integrations
description: Compose installed plugins and tools in app-owned integration modules
---

ChatJS separates installed registrations from application behavior. You own the domain-specific modules in `integrations/`. Adding, removing, or syncing plugins updates their generated inputs without rewriting these modules.

Start with a scaffold that includes these integration modules. An existing app using the older generated exports needs to adopt the modules and update its consumers explicitly. Sync does not migrate arbitrary application code.

## Ownership

Run `chat-js status` to inspect the ownership and local-edit state of installed plugin files. See [status](../cli/status) for the file tree, source states, and migration from older layouts.

| Location | Owner | What belongs here |
| --- | --- | --- |
| `plugins/<id>/chat.ts`, `plugins/<id>/billing.ts` | Installed plugin source, editable in your app | Plugin implementations |
| `chatjs/generated/installed-chat.ts`, `chatjs/generated/installed-billing.ts` | Installer | Static imports and typed adapter lists |
| `integrations/chat.ts`, `integrations/billing.ts` | Your app | Selection, ordering, wrappers, and local adapters |
| `lib/compose-chat.ts`, `lib/compose-billing.ts` | Your app | Shared composition rules and defaults |
| Routes, queries, and native runtime callers | Your app | Calls to the composed integration |

Keep local application modules outside `plugins/<id>/` when they should survive removal of that plugin. Generated lists do not contain callbacks, default policies, or application behavior.

## Chat lifecycle

The default composition is:

```ts
// integrations/chat.ts
import { installedChat } from "@/chatjs/generated/installed-chat";
import { composeChat } from "@/lib/compose-chat";

export const chat = composeChat(installedChat);
```

Callers import `chat` from `@/integrations/chat`. They do not enumerate installed plugins themselves. The composed interface exposes `onCreate`, `afterCreate`, `historyFilter`, `publicReadFilter`, `links`, `onDeleteConversations`, and `onDelete`.

To add app-owned behavior, put another adapter beside the installed list. For example, this adds a post-creation log:

```ts
// integrations/chat.ts
import { installedChat } from "@/chatjs/generated/installed-chat";
import type { ChatServerIntegration } from "@/lib/chat-plugin-contracts";
import { composeChat } from "@/lib/compose-chat";
import { createModuleLogger } from "@/lib/logger";

const log = createModuleLogger("app.chat");
const creationLog = {
  afterCreate: ({ conversationId }) => {
    log.info({ conversationId }, "Chat created");
    return Promise.resolve();
  },
} satisfies ChatServerIntegration;

export const chat = composeChat([...installedChat, creationLog]);
```

Installing a plugin later changes `installedChat`. Your local adapter remains in the composition. Put it before the spread when it should run first. Post-creation callbacks may repeat on recovery, so use an idempotent implementation when performing writes.

### Composition rules

| Operation | Rule |
| --- | --- |
| `onCreate`, `onDeleteConversations`, `onDelete` | Run sequentially in declared order using the caller's transaction. An error stops later adapters and propagates to the caller. |
| `afterCreate` | Run sequentially. Log each failure without exposing callback payloads and continue to later adapters. |
| `historyFilter` | Combine defined restrictions with AND. An empty list adds no restriction. |
| `publicReadFilter` | Combine defined grants with OR. An empty list returns false. |
| `links` | Merge results in declared order. Two adapters claiming the same chat cause an error. |

Core still owns authorization, transaction creation, lifecycle locks, pagination, and fallback title settlement. Composition does not open another transaction or turn post-creation work into a durable job. Public-read grants do not grant write access.

Use the supplied transaction for creation and deletion writes. Keep network calls outside those transactions. See [Plugin API](../reference/plugin-api) for each callback's timing and data contract.

## Billing

The default composition is:

```ts
// integrations/billing.ts
import { installedBilling } from "@/chatjs/generated/installed-billing";
import { composeBilling } from "@/lib/compose-billing";

export const billing = composeBilling(installedBilling);
```

`billing.canSpend(ownerId)` checks admission. `billing.debit` is either the selected adapter's transactional debit function or `undefined`.

- With no billing adapter, admission is allowed and debit is absent. Usage evidence is still recorded, but receipts are not marked charged.
- With one adapter, calls preserve its method receiver and propagate its results and failures.
- With multiple adapters, composition throws. Installation also rejects conflicting billing plugins before rewriting registrations.

Do not replace an absent debit with a no-op function. A successful debit allows core to advance the receipt's charged amount.

### Add an application spending rule

Wrap the composed policy in this same file. This example restricts paid turns to an application-owned allowlist while retaining the installed adapter's balance check and debit behavior:

```ts
// integrations/billing.ts
import { installedBilling } from "@/chatjs/generated/installed-billing";
import { composeBilling } from "@/lib/compose-billing";

const selected = composeBilling(installedBilling);
const permittedOwners = new Set(["your-owner-id"]);

export const billing = {
  ...selected,
  canSpend: async (ownerId: string) =>
    permittedOwners.has(ownerId) && (await selected.canSpend(ownerId)),
};
```

The wrapper continues to apply if you later install or remove the billing plugin. Replace the allowlist with your own policy when appropriate. Admission does not reserve money. Core retains usage deduplication, rounding, owner locks, and transactional settlement.

To supply an entirely app-owned billing adapter, pass it to `composeBilling` instead of `installedBilling`. That is an explicit selection: future installed adapters are not used by that composition.

## Installation and removal

Sync writes static installation lists and maps under `chatjs/generated/`. It does not rewrite `integrations/` or the composition helpers. Runtime callers keep importing the same app-owned modules as the installed selection changes.

Prefer importing the generated lists when your composition should follow installation automatically. If you directly import a plugin implementation to wrap it, your app now depends on that plugin. Removal detects supported static imports and requires you to resolve that dependency first. See [Create a plugin](./create-plugin) for packaging and installation metadata.

Keep chat lifecycle and billing modules safe for Next.js server code and native EVE. Do not import React, route handlers, or Next.js request helpers into them. Browser UI retains its separate [typed slot interface](../reference/plugin-api#client-slots).

## Integration points

All runtime consumers go through app-owned composition. There is no shared plugin runtime or discovery system: these are ordinary TypeScript modules, React slots, and native framework entry points.

| App-owned modules in `integrations/` | Responsibility |
| --- | --- |
| `chat.ts`, `billing.ts` | Compose lifecycle adapters and select billing policy |
| `chat-ui.ts`, `layout.ts` | Order or extend typed UI plugin lists; JSX slots still control placement |
| `authentication.ts`, `authentication-form.ts`, `sign-out.ts`, `signed-out.ts` | Select authentication policy, form, sign-out handler and signed-out screen separately |
| `navigation.ts`, `model-visibility.ts`, `uploads.ts` | Select navigation, model visibility and attachment hooks with explicit defaults |
| `tools.ts`, `tool-ui.ts`, `tool-providers.ts` | Compose native tools, renderers and shared provider definitions |
| `tool-availability.ts`, `tool-configuration.ts`, `composer-tools.ts` | Compose exposure predicates, client-safe schemas and display metadata |
| `document-ui.ts`, `document-actions.ts`, `document-run.ts`, `code-executor.ts` | Compose editors and assistant actions, select saved-document execution |
| `routers.ts`, `instrumentation.ts`, `database.ts` | Compose native tRPC routers, startup handlers and Drizzle schema paths |
| `session-profiles.ts`, `cleanup.ts` | Select persisted-session profiles and scheduled cleanup tasks |
| `plugin-catalog.ts`, `tool-catalog.ts` | Client-safe installation names and document kinds |
| `gateway.ts`, `storage.ts`, `sandbox.ts` | Wrap the installed native provider factories |

Each file imports the matching generated input and exports the app's selection. Gateway, storage and sandbox use their installed implementation modules directly rather than a generated registry. Their lifecycle and credentials remain in the provider implementations and runtime callers.

### Add or wrap tools

Add a native EVE definition to the object in `integrations/tools.ts`, retaining the installed inputs and workflow-name guard. Add its renderer to `integrations/tool-ui.ts`. An explicit object property after a spread can replace an installed definition or wrap an installed renderer. Installed descriptors still reject duplicate names; dynamic tools cannot shadow native workflow names.

Update `integrations/tool-catalog.ts` for an app-owned tool that should participate in selection, and `composer-tools.ts` for its display metadata. Keep these modules browser-safe. The catalog cannot import the server tool map to infer names: that would pull provider implementations and credentials into the client graph. There is no automatic discovery of arbitrary app-owned tools.

### Wrap UI

For a renderer, retain the installed map and replace one entry with a normal React component:

```tsx
// integrations/tool-ui.tsx (rename the scaffold's .ts file when adding JSX)
import { installedToolUi } from "@/chatjs/generated/ui";
import { defineToolRenderer } from "@/lib/ai/define-tool-renderer";
import {
  wordCountInput,
  wordCountResult,
} from "@/tools/chatjs/word-count/schemas";

const WordCount = installedToolUi["tool-wordCount"];
export const ui = {
  ...installedToolUi,
  "tool-wordCount": defineToolRenderer({
    inputSchema: wordCountInput,
    outputSchema: wordCountResult,
    render: (props) => (
      <section aria-label="Word count">
        <WordCount {...props} />
      </section>
    ),
  }),
};
```

This example requires the word-count renderer to be installed. Tool renderers must use `defineToolRenderer`: a plain React wrapper lacks the validation marker and is intentionally rejected when rendering persisted messages. A wrapper that imports a concrete plugin directly makes removal depend on updating that import. Keep shadcn primitives in `components/ui/` close to upstream; compose application UI above them.

Exclusive integrations reject multiple selections. Hook implementations are selected at module scope, never by looping through hooks during rendering. Session profiles must have unique authenticator identities; cleanup tasks must have unique IDs, including core tasks.

## Native entry points and migration

Next.js routes, EVE entry files and database migrations keep their native file conventions. Installing those files can activate behavior without a composition list. Plugin descriptors and `chat-js status` identify their ownership; integration modules do not intercept framework discovery. Removing a plugin retains its database schema history.

Apps with the older generated exports or `composition/custom/` files must explicitly adopt the new modules and update callers before sync. Move local tool and renderer registrations into `integrations/tools.ts` and `integrations/tool-ui.ts`; preserve their behavior rather than overwriting them with scaffold defaults. After updating consumers, remove the obsolete generated behavior files named by the layout error, then run sync and app checks. Preserve receipts and user source. Sync does not rewrite arbitrary user source.

When automatic installation conflicts, `chat-js add <item> --files-only` exports raw source and connection metadata into a temporary review directory. Review and copy selected files, adapt aliases/dependencies, and connect them through these app-owned modules. The export does not install or activate the plugin. See [add](../cli/add).
