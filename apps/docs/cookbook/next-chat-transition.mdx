---
title: Native EVE Conversations
description: How the EVE-backed app creates, resumes, and recovers conversations
---

ChatJS uses EVE as its conversation runtime. The browser connects through the authenticated ChatJS gateway, while EVE owns the durable transcript, execution state, approvals, and stream recovery.

ChatJS stores application-owned records around that runtime: ownership, project membership, titles, sharing, file ownership, document revisions, and billing evidence. Those records do not mirror the EVE transcript.

## First message and recovery

For a new conversation, the composer records a durable creation request before it asks ChatJS to create the EVE session. The page then navigates to `/chat/:id`. If the request is interrupted, the retained request can recover or retry without treating an uncertain network response as proof that creation failed.

An existing conversation starts `useEveAgent` with its EVE session ID and resumes from the durable stream position. The client does not mount a second chat runtime or reconstruct an AI SDK stream from local message state.

## Boundaries

| Boundary | Owner |
| --- | --- |
| Native messages, turns, approvals, checkpoints, and stream position | EVE |
| Authentication, ownership, projects, sharing, billing, files, and document revisions | ChatJS |
| Model calls, storage, and sandboxes | Configured providers |

The same route family serves new conversations, registered-user project conversations, guest conversations, and public read-only shares. EVE history is the source for the sidebar and search.

## Important limits

Lifecycle and hosting validation still determine whether a deployment is ready. The EVE-only runtime design does not by itself establish provider deletion coverage, guest-hosting readiness, or production release approval.
