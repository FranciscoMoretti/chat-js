# Main's thread and branch semantics: evidence for the EVE migration

Research date: 2026-09-20. Baseline: `4584f093835f1667c010c8fc20c502fa3f2bde41` (`origin/main` snapshot supplied for this investigation). This is source analysis, including regression-test inspection, not a claim that a browser verification was run. No application code was changed for this note.

## Identity is not one hierarchy of interchangeable IDs

| Identity | Meaning on main |
| --- | --- |
| `chatId` | Logical app chat, shared by all message branches. |
| runtime ID | Encoded `chat:<chatId>:thread:<threadId>` registry key. Normal UI uses `threadId = "main"`. |
| `Thread.id` | Set to the parsed **chat ID**, not the runtime thread ID. Every per-run AI SDK chat uses this same ID. |
| message ID | Stable tree-node identity. Parent edge cannot be changed once the node exists. A root has a null parent. |
| `cursorId` | Selected terminal message; the visible transcript is its ancestor path. It can select an intermediate node or null, not just a leaf. |
| run ID | Independently generated execution identity in an in-memory registry. Exists before an assistant message exists. It is not a branch ID or server stream ID. |
| parallel group/index | App metadata identifying a comparison group and model slot, independent of run and message IDs. A slot can have multiple retry messages. |
| request ID | Generated independently for each parallel request specification. |

Sources: [runtime ID encoding](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/chat-runtime-id.ts#L1-L27), [ApplicationThread construction](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/app-chat-runtime.ts#L98-L137), [per-run transport chat ID](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/ai-sdk-run-chat.ts#L132-L202), [draft identity generation](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/draft-chat-submission.ts#L49-L84).

**Main does not give every branch a persistent branch ID.** The core model is a message forest, node IDs and parent edges, plus one cursor. A branch is a path derived from those edges. The separate runtime `threadId` field is not evidence of one controller per message-tree branch.

## Tree selection and ordering

`MessageTree` stores messages, parents, ordered children and one cursor. `getPath` walks parents from that cursor. `getSiblings` returns all children of the same parent, including root siblings. `getLeaves` traverses descendants depth-first. Nodes are cloned on reads; snapshots contain only `version`, `nodes` and `cursorId`, not execution records or a per-parent selection map. A repeated message ID updates content in place but cannot move to another parent. Cycles and missing parents are rejected at this core boundary. [Implementation](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/message-tree.ts#L7-L187).

The app's `useSwitchToSibling` and `useSwitchToMessage` select the **last depth-first descendant leaf** of the requested sibling, falling back to the sibling itself. They do not remember the previously selected child separately for every parent. A product decision to remember per-parent selections would be a new behavior, not literal main parity. [Switching hooks](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/stores/hooks-threads.ts#L72-L98), [message selection](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/stores/hooks-threads.ts#L178-L193).

Ordering has two layers. Live concurrent runs reserve sibling order when starting, so reversed response arrival does not reverse the choices. Hydration orders siblings by parallel index within the same group, otherwise creation timestamp. Hydration's default cursor is the newest timestamp message, whereas switching an existing sibling chooses its rightmost DFS leaf. Those are distinct policies. [Live ordering](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/run-registry.ts#L96-L120), [reservation](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/run-registry.ts#L239-L248), [hydration](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/thread-utils.ts#L51-L65), [sibling sorting and snapshot construction](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/thread-utils.ts#L123-L220).

`setMessages` reconciles a selected path into the tree; it does **not** delete hidden siblings or descendants. `restore` replaces the entire tree, clears run records and refuses to run while executions are active. The snapshot builder recovers malformed persisted parent metadata so messages do not disappear; this is app hydration tolerance, not permission for invalid core edges. [Core mutation semantics](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L321-L334), [hidden-branch regression](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/test/thread.test.ts#L280-L300).

## Sending, editing, regeneration and continuation are different operations

- Sending normally attaches a fresh user node to the selected cursor and starts a run from that user. `from` can explicitly target another cursor; `follow` defaults to whether that target equals the active cursor. `from: null` starts a new root. Sending an existing message ID retains its original parent, which is why the app must generate a new ID for an edit. [Core startRun](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L366-L429).
- Editing in the app selects the old message's **parent**, generates a fresh user message ID, and sends from there. The old user message and its whole continuation remain as an alternative subtree. An edit to the first user message creates another root. The misleading comment “Trim messages” refers to the visible cursor path, not deletion. [Composer edit flow](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/components/multimodal-input.tsx#L453-L525), [fresh message ID](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/draft-chat-submission.ts#L72-L84).
- Regeneration creates a fresh assistant sibling under the original assistant's parent. Old output is retained. It keeps the original selected target visible until the new response binds, and does not steal selection after the user navigates elsewhere. [Implementation](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L241-L291), [regeneration and navigation tests](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/test/thread.test.ts#L705-L775).
- `sendMessage()` with no input on an assistant means **continue that same assistant node**, not regenerate. Tool output and approval updates route to the owning run regardless of the selected path. A bare `startRun()` from an assistant is forbidden; the library nevertheless supports persisted assistant-to-assistant edges and root assistants. Avoid conflating the app's more restrictive retry UI with the generic tree's capabilities. [Continuation dispatch](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L336-L364), [tool ownership reconstruction](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L634-L695), [app retry restrictions](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/chat-tree-actions.ts#L22-L65).

## Runs, selection and parallel responses

One thread supports many concurrent runs, including multiple runs from the same user message. Defaults impose no concurrency limit. A submitted run is a real execution before there is any assistant node; the stream may choose the response ID. Each run writes only its own response under its fixed parent. Selection follows incoming output only if that run is explicitly selected and the cursor still equals its initial target. Switching the cursor clears explicit run selection without canceling anything. `onFinish` receives the finishing run's path, not the currently visible path. [Write/follow condition](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L182-L237), [concurrency defaults](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/run-registry.ts#L22-L47), [pending/concurrent tests](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/test/thread.test.ts#L114-L160), [background navigation tests](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/test/thread.test.ts#L301-L336).

`status`/`error` describe the selected execution; `treeStatus` aggregates all submitted/streaming executions and ignores historical errors. `stop()` stops the selected run, `stopRun` one named run, and `stopAll` all active runs. Moving the visible path must not silently redefine all these controls as “stop this chat.” [Snapshot and stop behavior](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L432-L498), [selection resolution](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/run-registry.ts#L123-L169).

App comparisons create the user node once with the primary run, then start other runs from that same user with `follow:false`. Authenticated secondary transports wait for a correlated user-persistence acknowledgment; allocating the run does not mean the network request has started. Pending cards are indexed by group/slot to run ID before assistant IDs exist. Card display favors the selected response for its slot, otherwise the most recent response in that slot, so retries need not become separate comparison groups. [Parallel launch/gating](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/parallel-chat-requests.ts#L175-L264), [group projection](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/stores/hooks-threads.ts#L100-L151), [slot response resolution](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/thread-utils.ts#L16-L38).

## useThread is an observer/controller binding, not branch navigation

In owned mode, `useThread({id,...})` keeps its controller until `id` changes; changing callbacks updates dispatchers, but changing transport or initial messages with the same ID does not reconstruct it. In external mode, supplying a different controller object switches subscriptions; even a retained `setMessages` function is redirected to the newest thread. The hook does not stop the old controller on switch/unmount. `resume:true` calls resume for each new thread instance, not only on the hook's first mount. [Hook implementation](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/use-thread.ts#L183-L288), [switch/callback/resume tests](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/test/use-thread.test.ts#L166-L280).

The app uses the external-controller mode via its store wrapper, which installs current transport/callbacks on the existing `ApplicationThread`. Thus **branch switching changes a cursor in the same controller**, while changing the supplied thread means switching controller instances (normally different app runtimes). One state adapter cannot be shared by two controllers. [Wrapper](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/stores/base/use-chat.ts#L85-L138), [exclusive state ownership](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L105-L130).

Branch switching also flushes rendered message IDs and their lookup index **atomically**, bypassing normal message-content throttling when the selected path changes. This prevents a one-frame disappearance of user messages. An EVE adapter that updates selected path IDs before filling the message lookup can recreate the visual bug even without navigation. [Atomic projection](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/stores/with-thread-state.ts#L51-L79), [regression test](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/apps/chat/lib/stores/zustand-thread-state.test.ts#L160-L194).

## Hydration and resume

A tree snapshot contains no live run registry. Restoring an assistant can reconstruct a new run for its existing message ID, including tool/approval ownership. `resumeStream` resumes the selected run or reconstructs one for the selected assistant; it does **not** inherently resume every background branch. Reconnection refreshes that run's canonical path first. Full replay replaces prior canonical content without duplication; suffix continuation preserves the existing message ID, metadata and parts. [Resume/restore](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L306-L324), [reconstructed runs](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/abstract-thread.ts#L698-L748), [replay distinction](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/src/ai-sdk-run-chat.ts#L137-L185), [resume tests](https://github.com/FranciscoMoretti/chat-js/blob/4584f093835f1667c010c8fc20c502fa3f2bde41/packages/thread/test/thread.test.ts#L500-L663).

## Recommendations for translating these semantics to EVE

These are architectural deductions, not claims about EVE guarantees:

1. Retain one app chat identity and a chat-scoped message-tree display projection. An EVE session per branch can implement execution, but it is not a replacement for logical message identity, ordering, siblings, selected cursor, comparison slots, or per-run controls. This does not require making that projection the model transcript or duplicating EVE's transcript authority: app-owned lineage/prefix references can stitch native transcripts for display while native sessions own execution history.
2. Define “branch” precisely before schema changes. A session that keeps accumulating turns is a mutable continuation. A user can select an earlier message inside that session; sending there must create a new continuation, not accidentally append after its current tail. A branch/session ID alone cannot specify every cursor state main supports.
3. Preserve shared-prefix message identities across session forks. If EVE copies or reidentifies native messages, introduce an explicit mapping from `(sessionId, nativeMessageId)` to logical message IDs and fork boundary. Do not infer shared nodes by equal text or collapse distinct retries with identical text.
4. Model pending execution before native response ID or bound session availability. Comparison ordering and stop/error UI must work in that interval; operation IDs, run IDs, branch IDs and message IDs have separate jobs.
5. Keep a stable chat controller above the rendered route. Let branch/session observers feed its canonical graph without stealing selection. A controller switch or view unmount must have an explicit policy for running work, rather than canceling it incidentally.
6. Preserve edit-as-user-sibling and retry-as-assistant-sibling; do not turn each action into another sidebar chat. Preserve comparison group and slot across retry. Continue/tool-resume must update the same response identity where main does.
7. Apply selected path, message index and visible status in one projection update. Keep selected execution state separate from aggregate background activity.
8. Test delayed first chunks after branch switching, reversed candidate arrival, editing first/earlier messages, nested retry branches, returning to a sibling with descendants, selecting an intermediate cursor, retry within a comparison slot, stopping one of several runs, stream replay versus continuation, and tool approval from an unselected branch.

Unresolved by this core-library investigation: EVE checkpoint granularity at user/assistant/tool boundaries; native message identity across forks; continuation after checkpoint copy; whether active sessions can be observed without mounting multiple hook controllers; exact cross-tab/server persistence policy for cursor selection. These need EVE-side evidence before choosing the final adapter/schema. Main's current rightmost-leaf selection and lack of per-parent memory should not be silently upgraded under a parity claim.
