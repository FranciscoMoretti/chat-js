# ChatJS Create native shadcn handoff

W1 decision and experiment results, 25 October 2026. Based on ChatJS `9c7d39254` and its installed shadcn CLI `4.21.0`.

ChatJS Create will use shadcn's own preset model and CLI semantics. It will reuse ChatJS's existing installation selection for app features. W1 adds no production schema, theme flags, preset format, or configuration package. The experiment establishes the handoff needed by W6 and W7; those later packages implement the CLI forwarding and website.

## Ownership

| Concern | Existing authority | Use in Create |
| --- | --- | --- |
| Visual control values and types | `shadcn/preset`: `PresetConfig`, `PRESET_*`, `encodePreset` | Import directly; do not copy enums, defaults, or encoding into ChatJS |
| Primitive library | `PresetBase` and `PRESET_BASES` from `shadcn/preset`; native `--base` | Keep separate from the preset code, as upstream does |
| Preset validation and application | Native shadcn CLI | Forward original argument values; preserve upstream errors and semantics |
| Resolved visual configuration | `components.json`, global CSS, and font setup generated by shadcn | No parallel theme object in `chat.config.ts` |
| Installed features and providers | `installationSelectionSchema` in `packages/registry/installation.ts` | Reuse its existing fields: `plugins`, `tools`, `gateway`, `storage`, `sandbox` |
| Installation compatibility | Existing `planInstallation`, provider resolution, and registry metadata | Reuse them; do not duplicate their dependency rules in a browser-side planner |
| Runtime app settings | Existing app configuration schema and generation | Keep auth/runtime options outside the visual preset and installation schema |

The existing installation schema is strict and rejects unrelated theme fields. It already has the small input shape needed here. There is no need for a new versioned `CreateConfig` wrapper, `ChatJSPreset`, theme manifest, or custom theme settings command.

## Native CLI handoff

Use the installed shadcn executable for `init` and `apply`. Its commands are not a documented programmatic API; importing private command implementations would couple ChatJS to internals. Public preset and registry subpath exports are suitable for the website and metadata work. See the [upstream API reference](https://ui.shadcn.com/docs/registry/api-reference) and [CLI reference](https://ui.shadcn.com/docs/cli).

For W6, use an explicit `--` boundary to forward native shadcn initialization arguments. This avoids cloning the upstream option parser into ChatJS or accidentally interpreting a misspelled ChatJS option as a theme setting. Example of the intended future invocation, **not implemented by W1**:

```bash
bunx @chat-js/cli create my-chat --yes --gateway openrouter -- --preset b27I2r8C --base base
```

Everything after the boundary retains native spelling, values, ordering, optional values, and positive/negative forms. Shadcn parses and validates those arguments. ChatJS does not translate a preset into separate colors, font, radius, or icon options. For a newly supported upstream theme switch, the forwarding path should not need a new ChatJS schema field.

ChatJS still owns the destination and app scaffold. Directory/framework/lifecycle switches such as shadcn's `--cwd`, `--name`, `--template`, monorepo creation, and forced reinstallation are not visual configuration for this handoff. W6 must reject conflicting topology/lifecycle arguments before creating files, resolve the destination once, and invoke shadcn there. Do not silently replace those arguments or allow native initialization to write a second project. The documented visual pass-through must not be described as support for every shadcn subcommand or every app framework.

Preserve native preset behavior, including named presets, preset codes, the separately selected base, CSS-variable/RTL/pointer choices where supported, and upstream errors. The release compatibility matrix still determines which library/style combinations ChatJS actually supports; W0 recommends Base UI/Rhea first and W9 covers complete dual-library support. A native option being accepted by shadcn does not prove ChatJS's application code supports it.

Existing apps continue using normal native commands such as `shadcn apply <preset> --only theme` or `--only font`. W1 introduces no ChatJS command wrapping those operations. No ChatJS defaults override upstream theme defaults. A selected ChatJS launch preset is an explicit preset choice; it is not a redefinition of shadcn's defaults.

W6 must place native initialization before installing selected registry UI, then preserve that configuration through later installations and sync. It must compare initial scaffold components to the selected preset and handle reinstallation deliberately: `--no-reinstall` alone cannot make existing component source match a different style. That integration depends on W2's modernized foundation and is not proven by this minimal fixture.

## Existing installation choices and handoff gaps

Use the existing command and registry semantics. Do not add a general configuration-import mechanism just to carry a visual preset.

| Choice | Current noninteractive interface | W6 and W7 consequence |
| --- | --- | --- |
| Gateway | `--gateway` accepts existing names/addresses | Reuse provider catalog and resolver |
| Uploads, MCP, projects | Positive/negative feature flags | Preserve their existing installation mappings |
| Documents | `--documents` / `--no-documents` | All-or-none is reproducible today; per-document-kind UI needs a deliberate installation handoff |
| Search, URL retrieval, code, image, video tools | Existing tool-address flags | Preserve slot validation and provider requirements |
| Storage | `--storage-provider`, non-secret `--storage-config` | Keep credential setup in environment variables |
| Sandbox | `--sandbox-provider` | Keep tool prerequisites in the existing planner |
| Observability | `--observability` | Reuse installed items and existing validation |
| Electron | `--electron` / `--no-electron` | Preserve current scaffold behavior |
| Auth providers | Interactive prompt; `--yes` uses current defaults | Arbitrary website auth choices do not yet round-trip through `create` |
| Arbitrary plugins/tools, feedback, follow-up suggestions, deep research, selected document kinds | Planner/registry inputs exist; create flags do not cover every interactive choice | Resolve in the installation lane against existing selection inputs, not by adding theme fields |
| Existing repository | `--from-git` preserves cloned source and rejects selection flags | Do not apply Create selections to this path implicitly |

At this revision, documents default on, uploads/MCP/projects/observability default off, and authentication comes from the existing authentication defaults. Reuse the authoritative defaults rather than copying this prose into website code. The launch website must only offer choices its emitted installation commands can reproduce; missing inputs are concrete W6 integration work.

The active CLI validation effort is in a separate `registry-validation-alignment` worktree and changes scaffolding and dependency validation. W1 does not edit or import those unmerged files. W6 should start from the merged implementation and reuse its installation generation/validation rather than developing a competing assembly path.

## Experiment and results

Run from the repository root after `bun install`, with Node 24 or newer and Playwright Chromium available:

```bash
bash docs/architecture/experiments/shadcn-create-contract.sh
```

The script creates an isolated Next.js fixture, invokes the repository's installed shadcn executable, bundles the actual public preset module and existing ChatJS installation schema for the browser, and executes the bundle in Chromium. It retains logs and `results.json` in the temporary directory printed by the script. It does not alter the repository's app or dependencies.

Verified with CLI `4.21.0`:

1. The browser imports the native preset model and option lists without Node-only polyfills. The observed catalog has eight styles, 25 themes, 26 body fonts, five radii, and five icon libraries; the UI must read the exports rather than freeze these counts.
2. The browser encodes Rhea/neutral/blue/Inter/small-radius/Lucide as `b27I2r8C`. Native `init --preset b27I2r8C --base radix` creates `radix-rhea`. Native `preset resolve --json` returns exactly `b27I2r8C`, with no fallbacks.
3. Native `--no-rtl` and `--pointer` are applied without ChatJS interpretation. A subsequent native `add button` works against the selected configuration.
4. Applying a second preset with `--only theme` changes blue to rose and the radius to large while preserving Inter and the button source byte-for-byte. Its resolved code is `b27LARay`, representing the retained font rather than the second preset's Geist choice.
5. Theme-only application preserves the `@chatjs` registry namespace, a sample `chat.config.ts`, font layout source, and the native pointer rule.
6. Native `apply not-a-real-preset --yes` exits with an upstream invalid-preset error. No ChatJS validation or aliasing is needed.
7. The existing `installationSelectionSchema` parses and round-trips uploads, OpenRouter, and S3 configuration in Chromium, including its existing defaults. It rejects a theme field. This proves browser suitability and serialization, not an actual OpenRouter/S3 installation.
8. The generated minimal Next.js fixture typechecks.

The script invokes CLI `4.21.0`, but native initialization resolves live registry data and writes `shadcn: ^4.22.1` into the generated fixture. Pinning the invoking CLI does not pin every generated dependency or remote registry payload. W6/W8 should record resolved versions and test the emitted app; they must not claim byte-identical generations from a floating registry.

## Ready for the next packages

W1 is complete as a bounded design and integration experiment. W6 can implement native argument forwarding and installation handoff after W2; W7 can build controls from upstream exports and existing installation inputs. Neither needs a new visual contract. Preview correctness across style/icon/font changes and full application preset compatibility remain W2/W7/W8 acceptance work.
