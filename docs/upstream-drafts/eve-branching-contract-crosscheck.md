## History: read is supported in callbacks; structured seed is missing

Do not report that EVE has no public structured history read. Both pinned and released EVE expose `MemoryOperationContext.messages: readonly ModelMessage[]`; memory providers can read it at `turn.completed` and `compaction.requested`. `DynamicResolveContext.messages` also exposes the history visible at that resolve point. These are retained/model-context reads at execution callbacks, not a general authenticated API to fetch an arbitrary historical prefix with stable application message identities. Compaction and contextual projection make that distinction consequential. [Pinned memory contract](https://github.com/vercel/eve/blob/247b3f05244893170bcf4dbcf20a2e35e416ccee/packages/eve/src/public/memory/index.ts), [released dynamic contract](https://github.com/vercel/eve/blob/a59a8f4f811520d44fcdbb26e7ed33d3b859b99b/packages/eve/src/dynamic/definition.ts).

The public memory recall return accepts `{ messages: [{ content: string, id?: string }] }`, not role-preserving `ModelMessage[]`. Instructions accept text with system/user roles; client context is explicitly ephemeral and excluded from durable history. None is an equivalent import of paired assistant tool calls, tool results, attachments and selected user/assistant history. [Memory return type](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/public/memory/index.ts), [instructions](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/shared/instructions-definition.ts), [client input](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/client/types.ts).

Released `0.59.1` adds public idle client creation (`CreateSessionOptions` contains request headers and cancellation only). Pinned `0.52.2` does not have that client option; do not project the newer public client feature backward. Neither version's client creation/send contract provides structured native history seeding. Internal session creation does have `turnAgent.initialMessages`, but bootstrap derives those from compiled instructions; it is not an authored native-transcript import. `createSessionStep` has no seed parameter. [Released client](https://github.com/vercel/eve/blob/a59a8f4f811520d44fcdbb26e7ed33d3b859b99b/packages/eve/src/client/types.ts), [internal bootstrap](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/runtime/agent/bootstrap.ts), [session creation](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/execution/create-session-step.ts).

Inference: for fresh-session branching at a settled boundary, the smallest missing capability is a supported, validated, idempotent structured-history seed. A native prefix/export contract is additionally needed if ChatJS must derive arbitrary older branches from EVE's authoritative history without retaining a second synchronized model transcript. A callback capture may suffice for deliberately restricted captured boundaries, but does not by itself prove exact historical edits/regenerations across compaction, cancellation and partial tools.

Callback export can avoid a second _mutable_ transcript if each capture is an immutable boundary record and ChatJS never attempts to reconcile it back into the running EVE session. It still duplicates some native history bytes and needs a defined mapping from application message IDs to model boundaries. Public callback `ModelMessage[]` does not specify stable message/node IDs or a pre/post-compaction identity map; turn IDs and operation IDs identify operations, not each history node. The memory lifecycle explicitly projects history before capture, and completion capture errors are caught/logged. Therefore this path cannot be treated as guaranteed transactional export or as a reason to mark a failed app capture ready. [Memory projection and operation IDs](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/context/memory-lifecycle.ts), [capture failure handling](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/context/memory-event-lifecycle.ts).

An app-owned immutable prefix reference can prevent app database message duplication. It does not prevent EVE from materializing/copying that prefix internally; EVE currently constructs session history as an array. Native zero-copy prefixes would require another storage contract and should not be bundled into the minimum feature-preserving seed request. [History initialization](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/execution/session.ts).

## App-authored Workflow does not make private steps public

EVE ships atomic durable `turnStep` and `createSessionStep` implementations, so a fresh execution need not clone an entire Workflow run. However, neither is a supported package export in the inspected versions. A file being present in npm `dist` is not a public contract. Public workflow tools and the `workflow`/`workflow/api` ambient module bridge allow authored durable work; they do not expose ownership of EVE's session driver, inbox, state persistence, cancellation and task lifecycle. [Pinned exports](https://github.com/vercel/eve/blob/247b3f05244893170bcf4dbcf20a2e35e416ccee/packages/eve/package.json), [HEAD exports](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/package.json), [durable turn step](https://github.com/vercel/eve/blob/247b3f05244893170bcf4dbcf20a2e35e416ccee/packages/eve/src/execution/workflow-steps.ts), [module bridge](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/public/workflow-modules.d.ts).

Inference: an upstream-supported session-driver API could let ChatJS author the outer workflow and reuse these steps. That is an alternative extension, not a zero-extension workaround. It increases app/scaffold responsibility unless EVE continues to own the driver. Prefer the narrow seed/export boundary when the objective is reducing total maintained complexity. No evidence here requires full execution cloning for settled fresh branches; live approvals/tasks require separate semantics.

## Sandbox: public backend is viable; a global capture barrier is app work

`SandboxBackend` is explicitly public and supports app implementations. Its `create` receives session key and existing metadata, while `captureState` returns a reconnect record. That record is not specified as an immutable historical snapshot. An app backend can maintain independent snapshot records and resolve a child session key to a chosen immutable snapshot without exposing private EVE internals. Public `getSandbox()` returns operations, not a historical snapshot/restore API. [Backend contract](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/shared/sandbox-backend.ts), [callback sandbox access](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/context/session-context.ts).

The event sink emits/writes the event before awaiting memory lifecycle and authored hooks. Thus a client observing `turn.completed` cannot assume those writers have finished. Awaiting a completion hook also cannot prove every process, background task, external editor or provider operation is quiescent. [Event sink ordering](https://github.com/vercel/eve/blob/da82a953dc62fcce8a3684e4eed7a8b693b0941d/packages/eve/src/execution/session/event-sink.ts).

Required app design (inference): close mutation admission for a specific revision; drain or explicitly reject every registered writer including background processes; capture immutable state; durably mark a uniquely keyed checkpoint ready only once its manifest and provider result exist; reconcile pending/failed records after crashes; restore a child into a separate sandbox identity; then reopen the parent. A backend wrapper only proves coordination for operations routed through it. Unregistered writers must be prohibited or explicitly unsupported. Between-turn edits need their own revision boundaries; failed/cancelled turns need an explicit policy; pending approvals/background tasks cannot silently become ordinary completed checkpoints.

The installed SDK's `Sandbox.snapshot()` declaration explicitly says it stops the source sandbox and returns a snapshot usable by `createFromSnapshot`. Therefore capture is not a transparent read: parent continuation requires reattachment/restart or replacement plus correct persisted handle metadata, and in-flight process continuity is not established. The SDK declaration alone does not prove safe process recovery, immutable retention duration, or crash atomicity. These need a later real-provider acceptance test; none was allocated here. [Installed SDK declaration](/Users/fran/.codex/worktrees/1a4e/chat-js/node_modules/@vercel/sandbox/dist/sandbox.d.ts:1067).
