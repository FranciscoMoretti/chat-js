## Boundary of responsibility

EVE provides generic durable-session mechanics. ChatJS supplies all product policy around those mechanics. In particular, `authorizeFork` receives a verified EVE principal but ChatJS decides whether that principal owns the bound source. EVE restores native model/display history, while ChatJS persists operation identity, ancestry, selected model, usage/credit treatment, and application resources. Sandbox identity evidence is a native/local primitive; ChatJS's deletion coordinator still owns family coverage and external-resource policy.

## Source and compiled patch audit

`patches/eve@0.52.2.patch` reverse-applies against this checkout's installed EVE package. That validates the installed artifact contains the patch. The readable source inputs now include `patches/eve-approval-receipts.source.patch`, reconstructed from the installed receipt helper and its call sites. It applies after the checkpoint and collector patches against the pinned tag.

The reconstruction was checked with `git apply --check` in a clean source-patched worktree and then compiled there with Node 24: both `build:types` and `build:js` passed. The worktree used a new dependency tree from the existing local pnpm store, so it was isolated but not a clean-cache install. The four existing ChatJS native approval-contract cases also passed when aliases loaded the rebuilt EVE modules. They cover exact session/call/tool/input matching, stale/denied/ambiguous data, and owner/foreign harness behavior. No EVE-native source test has been added yet, so upstreaming still requires moving or duplicating that focused behavior into EVE's own source tests.

The source build must apply patches in the sequence stated in [patches/README.md](../../patches/README.md). The collector patch has package-relative paths and must run with `packages/eve` as the working directory. The next gate is comparison with a dedicated unpacked published package and a clean Bun-cache installation whose installed modules reverse-apply the compiled patch. Relocated root helpers are a packaging workaround for Bun 1.3.11; source paths stay normal. The current AST-level check found the same receipt helper calls and arities, the same three-argument `approval` lookup, and the same four-argument receipt preparation call in rebuilt and installed modules. It does not establish full semantic or byte equivalence; the direct diff still contains the deliberate root-helper relocation and rewritten imports, plus content-addressed chunk names and the vendor stamp.

## Upstream plan

The full test-inclusive EVE `typecheck` was attempted and is not green. Failures include snapshot fixtures still using version 1 where version 2 is required, transcript seed/prefix authenticator types, an unused `getRun` binding in the fork integration test, and compaction/public-channel typing. These are outside the reconstructed receipt files but remain this maintained fork's responsibility. The successful production declaration/JavaScript builds and four approval contracts do not substitute for repairing that suite.

1. Run the reproducibility gate and add focused EVE source tests for approval continuation and receipt lifetime before proposing any code.
2. Split generic APIs into reviewable proposals: checkpoint/fork authorization; imported transcript seed/prefix; durable events; named readiness; sandbox snapshot/birth evidence. Keep collector metadata independent.
3. For each accepted release, rerun only its mapped native and ChatJS boundary tests, reduce the compiled patch, and retain ChatJS product-policy coverage.
4. Remove the root-helper relocation only after the supported Bun versions pass a fresh nested-file patch install and the source-to-dist comparison.

## Test-fixture cleanup recommendations

Do not remove tests to reduce size. Consolidate setup only where it preserves a real boundary:

- Keep the co-located `fixture()`/actor/session/batch setup in `apps/chat/tests/eve-mcp-native-approval.test.ts`: it has one consumer today. Extract it only when another native receipt contract needs the same setup. Keep the four receipt-mismatch assertions and the harness owner/foreign scenarios separate; they protect different receipt boundaries.
- Several browser specs independently create an owner conversation, but their setup also fixes different model, retry, cleanup, and source-history semantics. Establish an actually repeated owner-session contract before extracting a helper; do not generalize one from the current examples. Keep ordinary turn checkpoints, named idle checkpoints, and imported-message prefixes as separate assertions.
- Reuse `eve-attachment-fixtures.ts` for binary/PDF bytes across fork and copy coverage. Retain the native filesystem isolation assertion because a model response cannot establish that a fork reread its own bytes.
- Keep database lifecycle fixtures behind `assertEveTestDatabase`; this audit performed no database action. Any fixture extraction must preserve its isolated-local-database guard and must not turn a native unit regression into a database/browser test.
