# Native EVE registry: ChatJS semantic compatibility

Static inspection on 2026-11-11, ChatJS HEAD `4fc8f8cee`. No runtime source changed; no installers or live integration calls were run by this investigation. Generated-app installation/build evidence belongs to the parent compatibility experiment. Upstream links describe current main, not necessarily the pinned ChatJS fork.

## Finding

Native EVE capability discovery and successful compilation do not establish full ChatJS compatibility. The smallest common integration work is tool-selection policy, output dispatch, accounting policy, and identity handling—not rewriting every integration's execution implementation.

| Item | Concrete compatibility issue | Smallest appropriate adaptation |
| --- | --- | --- |
| `tool/web_fetch` | Official item simply re-exports `eve/tools/web_fetch`. It does not enter ChatJS's installed tool catalog, selected-tool filter, or tool cost receipt protocol. Its unnamespaced output can use the existing generic renderer. | Register selectable metadata only if desired; extend policy to native tools; explicitly decide how external costs are recorded. Keep native execution. |
| `connection/notion` | Uses `@vercel/connect/eve`, not ChatJS's persisted MCP connector/OAuth layer. Account auth already supplies a user principal, but Connect requires its own provisioning/grants. Namespaced native output is routed to a renderer requiring a ChatJS-specific envelope and can display false failure. | Keep native connection/auth; provision Connect, retain stable user mapping, support native output and consent UI, and apply common selection policy. |
| `channel/slack` | Native Slack identity does not satisfy the hard-coded ChatJS account authenticator. The root model/instructions then require a registered non-account session profile. Simply relabeling identity cannot create ChatJS's required conversation reservation/binding. | Deliberately support a separate Slack profile/agent, or implement verified Slack-user mapping plus a durable ChatJS creation/binding path. This is broader than adding the channel file. |
| `extension/agent-browser` | Needs a real process sandbox with Chromium/system packages; ChatJS can deliberately disable sandboxes. `browser__*` names are misclassified as ChatJS MCP results. Native extension tools bypass installed-tool filtering. | Use a compatible ChatJS persistent sandbox and initialization strategy; fix generic namespaced rendering and policy. Preserve ChatJS resource lifecycle rather than overwrite its sandbox file. |
| `memory/file` | Separate per-principal storage and generated `file__save_memory` / `file__remove_memory` tools. These names hit the same incorrect MCP dispatch. Default backend depends on EVE development mode or Vercel, not merely `NODE_ENV`. Cross-channel identity changes produce distinct memory scopes. | Configure backend explicitly for non-Vercel workers, choose identity/scope semantics, render native results, and define memory retention/account deletion separately. |

Official source: [web_fetch](https://github.com/vercel/eve/blob/main/apps/docs/registry/tools/web_fetch.ts), [Notion](https://github.com/vercel/eve/blob/main/apps/docs/registry/connections/notion.ts), [browser mount](https://github.com/vercel/eve/blob/main/apps/docs/registry/extensions/agent-browser.ts), [memory mount](https://github.com/vercel/eve/blob/main/apps/docs/registry/memory/file.ts), [Slack setup](https://eve.dev/docs/channels/slack).

## Shared boundaries in current source

**Selection/availability:** [agent.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/agent/agent.ts:31) sets `defaultTools: false`, but this disables defaults rather than explicitly authored registry tools. [installed.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/agent/tools/installed.ts:10) filters only the imported ChatJS execution set. [turn-tools.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/turn-tools.ts:31) applies the selected execution-name list there. The [model middleware](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/tool-availability.ts:13) only removes names present in ChatJS's availability map. Native files, connection tools, and extension tools therefore do not automatically inherit these UI restrictions. The [ChatJS MCP adapter](/Users/fran/.codex/worktrees/7b28/chat-js/packages/registry/src/plugins/mcp/src/runtime/agent-tools.ts:25) separately suppresses its tools when an explicit tool is selected; native Notion does not pass through that adapter.

**Rendering:** [EveMessagePart](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/components/eve/eve-message-part.tsx:166) routes any parsed namespace to `EveMcpResult`; [parseToolId](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/ai/mcp-name-id.ts:81) accepts any name containing `__`. The [result schema](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/mcp-result.ts:21) requires `kind: "chatjs.mcp-result"`, and [EveMcpResult](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/components/eve/eve-mcp-result.tsx:17) marks completed results failing this schema as MCP failures. This affects browser and memory tools as well as native MCP. Prefer envelope/metadata-based dispatch with the existing [generic fallback](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/components/eve/eve-message-part.tsx:46), not wrapping every foreign result merely to satisfy the wrong namespace assumption.

**Accounting:** [usage.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/usage.ts:20) treats outputs without a ChatJS tool receipt as processed and records no tool charge. [tool-result.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/tool-result.ts:55) identifies that receipt through `kind: "chatjs.tool-result"`. This is not an execution blocker, but foreign service/browser infrastructure costs do not become ChatJS usage entries automatically. Root model accounting remains on the existing [accounted model path](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/agent/agent.ts:42); do not claim all model billing is lost. Decide which provider costs ChatJS owns and add accounting at that common boundary only where needed.

**Slack identity and history:** [isAccountSession](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/session-identity.ts:13) requires persisted `authenticator === "chatjs-gateway"`. Other identities go through [requireSessionProfile](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/session-profile.ts:10), which rejects an unregistered authenticator. Account sessions trigger [conversation binding](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/agent/hooks/conversation.ts:22); [resolveEveConversationScope](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/conversation-scope.ts:71) requires an existing ownership row, and pending creation is verified against a native receipt. The [HTTP channel](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/agent/channels/eve.ts:9) also owns file retrieval and branch-history restoration. Preserve that channel; a new channel does not automatically gain its auth/history semantics. Billing and sandbox registration [skip non-account identities](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/agent/hooks/billing.ts:23).

**Connect:** [gateway-auth.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/gateway-auth.ts:168) already returns user type, stable owner ID, and issuer `chatjs`. [Connect documentation](https://vercel.com/docs/connect/frameworks/eve) maps user ID/issuer into separate per-user grants, requires project/OIDC configuration, and defaults runtime auto-provisioning off. Thus a new custom identity adapter is not inherently required for web users; existing ChatJS MCP OAuth grants do not automatically transfer. Native consent suspends/resumes EVE, but the current [pending-input UI](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/components/eve/eve-pending-input.tsx:115) renders prompts/options without a dedicated authorization URL/device-code treatment. Verify the actual pinned interaction payload before calling consent compatible.

**Browser execution:** [sandbox-environment.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/sandbox-environment.ts:12) explicitly blocks sandbox use when the selected provider lacks persistence. Otherwise [persistent-sandbox.ts](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/persistent-sandbox.ts:39) binds execution to ChatJS owner/session/reservation identity and [creates resources](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/persistent-sandbox.ts:235) through the app provider. [Browser documentation](https://github.com/vercel/eve/blob/main/packages/eve-agent-browser/README.md) requires real process execution and apt/dnf plus sudo for automatic system installation; just-bash cannot run Chromium. A provider's TypeScript compatibility does not prove its image contains these dependencies. Inline screenshots also need native-aware rendering to become images instead of raw output.

**Memory:** [File-memory docs](https://eve.dev/docs/memory/file) define storage outside the sandbox; EVE dev defaults to process-local memory, Vercel uses configured Blob, and other environments require an explicit backend. [Principal scope source](https://github.com/vercel/eve/blob/main/packages/eve/src/shared/principal-scope.ts) keys by current principal type/authenticator/issuer/ID, so web and Slack users are not automatically the same memory owner. ChatJS's inspected [conversation resource purge](/Users/fran/.codex/worktrees/7b28/chat-js/apps/chat/lib/eve/purge-local-resources.ts:36) covers code sandboxes, documents, and files, not this separate per-user memory store. That is not necessarily wrong—memory intentionally outlives conversations—but its retention and user deletion need an explicit policy.

## Test implications

In addition to install/type/build, exercise: web_fetch under an explicitly selected unrelated tool; successful native namespaced tool output; Connect consent and resumption; Slack's first model turn and ownership binding; browser launch/screenshots in the actual selected sandbox; memory persistence across separate sessions and backend restarts. These probes distinguish app-semantic failures from provider credentials, infrastructure prerequisites, and upstream package compatibility.
